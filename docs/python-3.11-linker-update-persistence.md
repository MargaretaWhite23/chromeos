# Python 3.11 shared-library repair and ChromeOS update persistence

**Observed:** 6 November 2026  
**Host:** ChromeOS 150, build 16700.66.0 (Official Build, `ltc-channel`), Fizz/Chromebox, x86_64  
**Status:** Python working after linker-cache regeneration; reboot persistence and update persistence **not experimentally verified**.

## Summary

The ChromeOS host initially could not start its Python 3.11 interpreter:

```text
/usr/lib/python-exec/python3.11/python3: error while loading shared libraries:
libpython3.11.so.1.0: cannot open shared object file: No such file or directory
```

The matching library existed at `/usr/local/lib64/libpython3.11.so.1.0`. Python 3.11.11 started successfully with `LD_LIBRARY_PATH=/usr/local/lib64`. The existing `/etc/ld.so.conf` already included `/usr/local/lib64`, so adding a directory to the configuration was **not necessary**. Running `/sbin/ldconfig` rebuilt the linker cache. Afterwards Python started without `LD_LIBRARY_PATH`.

**Repair that worked:**

```sh
/sbin/ldconfig
env -u LD_LIBRARY_PATH /usr/bin/python3.11 --version
env -u LD_LIBRARY_PATH /usr/lib/python-exec/python3.11/python3 --version
env -u LD_LIBRARY_PATH python3 --version
/sbin/ldconfig -p | grep 'libpython3.11.so.1.0'
```

**Verified result:** all Python version checks reported `Python 3.11.11`; linker-cache listing resolved the library to `/usr/local/lib64/libpython3.11.so.1.0`. The cache was updated at 2026-11-06 19:31:31 UTC.

## ChromeOS partitions and update risk

Read-only checks:

```sh
rootdev -s
lsblk -o NAME,SIZE,FSTYPE,LABEL,MOUNTPOINTS
cgpt show /dev/sda
mount | grep -E ' on (/|/usr/local) '
```

Observed layout:

| Partition | Label / role | Observed state |
| --- | --- | --- |
| `/dev/sda1` | `STATE` | ext4, mounted at `/usr/local` (also other stateful mounts) |
| `/dev/sda3` | `ROOT-A` | ext2, active root `/` |
| `/dev/sda5` | `ROOT-B` | ext4, alternate root |
| `/dev/sda2` | `KERN-A` | priority=1, successful=1 |
| `/dev/sda4` | `KERN-B` | priority=2, tries=6, successful=0 at observation time |

The `KERN-B` metadata suggests boot attempts are configured for the alternate slot, **not** definitive proof that an update is pending. Do not alter kernel priority or tries merely to test Python.

ChromeOS A/B updates can replace or switch the active root filesystem. Consequently:

- `/usr/local/lib64/libpython3.11.so.1.0` and the Python installation on stateful storage are normally retained across ordinary updates.
- `/etc/ld.so.cache`, `/etc/ld.so.conf` and `/etc/env.d` live on the root partition and can be replaced with the new image.
- The library can remain available on disk while Python fails after an update if the new root's linker configuration/cache cannot resolve it.
- Changes to `/etc/init` are **not** inherently update-safe: `/etc/init` is on the root filesystem.
- Presence of a script under `/usr/local` **alone does not mean it runs after boot/update**. A supported, update-resilient hook that runs after stateful storage is mounted must be identified and tested.

**Conclusion:** current functionality is verified; reboot persistence is likely but untested, and update persistence is **not guaranteed**. No reboot or OS update was performed during the investigation.

## Safe checks before or after an update

```sh
echo '=== OS and active root ==='
grep -E 'CHROMEOS_RELEASE_(VERSION|TRACK|CHROME_MILESTONE)=' /etc/lsb-release
rootdev -s
echo '=== library exists ==='
test -r /usr/local/lib64/libpython3.11.so.1.0 && echo LIBRARY_PRESENT
echo '=== search path and cache ==='
grep -F '/usr/local/lib64' /etc/ld.so.conf
/sbin/ldconfig -p | grep 'libpython3.11.so.1.0' || true
echo '=== actual Python start ==='
env -u LD_LIBRARY_PATH /usr/bin/python3.11 --version
```

If the library exists but normal Python invocation fails, test **without changing system files**:

```sh
LD_LIBRARY_PATH=/usr/local/lib64 /usr/bin/python3.11 --version
```

If this succeeds and `/etc/ld.so.conf` includes the expected trusted directory, `/sbin/ldconfig` was the successful repair on this build. Exercise caution after an update: verify the newly active root's configuration and ABI before changing its linker cache.

A repeatable **pre-update and post-update check** should record ChromeOS build, root device, library file/checksum, cache resolution, and actual Python startup; the post-update check necessarily requires booting an updated system and has not happened here.

## Separate finding: Python SQLite is not installed

`import sqlite3` fails with `ModuleNotFoundError: No module named 'sqlite3'`. The matching Python `sqlite3` package and compiled `_sqlite3` extension were absent, although `/usr/lib64/libsqlite3.so.3.49.1` exists. The official Python binpkg `dev-lang/python-3.11.11_p1-r2` has USE flags that omit `sqlite`; Python SSL and ctypes imports worked.

This is a **separate feature omission**, not evidence that the shared-library repair failed. Do not rebuild Python or install SQLite support unless a specific application requires Python's `sqlite3` module.

## Portage and binhost investigation

The development environment's `make.conf` uses `ROOT="/usr/local"`. The binhost `Packages` index was reachable and listed `dev-lang/python-3.11.11_p1-r2` with USE flags `abi_x86_64 amd64 elibc_glibc ensurepip gdbm kernel_linux ncurses pgo_use readline ssl userland_GNU`. The profile lists Python under `package.provided`, so a normal `emerge` attempt will not straightforwardly reinstall it. A `PORTAGE_BINHOST unset` warning was seen during tentative package queries. Output in the bridge rendered the binhost as a Markdown URL, but a byte-level comparison confirmed the actual file contains the correct plain URL.

Reinstalling the same binpkg would **not** add SQLite support.

## Future update-resistant mitigation (proposal only)

1. Prefer a supported ChromeOS dev-install or stateful startup mechanism over direct changes to replaceable `/etc/init`.
2. Place a small **idempotent** check/recovery script on stateful storage; first test `env -u LD_LIBRARY_PATH /usr/bin/python3.11 --version`.
3. Only if necessary and after checking that `/usr/local` is mounted, the library exists, and the linker config includes that directory, run `/sbin/ldconfig` and verify Python again.
4. Keep stateful logs of OS version, root slot, checks and results.
5. Test safely on the current OS and subsequently observe a real update to confirm the startup hook actually runs. Avoid assumptions about alternate-root contents or update timing.

**Not implemented.** This repository entry documents the findings and recommended approach; it does not install hooks, change boot slots, rebuild Python, update ChromeOS, or reboot.
